# Fix Plan — friction found during heavy agent use (2026-06-11)

Source: three days of intensive MCP-driven work on shadowdark-enhancer
(Phases 8–10: ~60+ `evaluate` calls, 8 reload cycles, 5 live verification
checkpoints, bulk migrations of 164 actors / 132 tables). Every issue below
was hit in real use; none are hypothetical.

> **Implementation report:** [FIX-IMPLEMENTATION-2026-06-11.md](./FIX-IMPLEMENTATION-2026-06-11.md)

Architecture refresher (for scoping):
- `server/proxy.mjs` → `server/server.js` → `server/lib/` (`bridges.js` WS
  registry, `foundry-rpc.js` request/timeout, `snapshot-store.js`) +
  `server/tools/*.js` (tool defs: `runtime.js`, `world-authoring.js`,
  `canvas.js`, `server-local.js`, …)
- `module/scripts/bridge.js` (~4.2k lines) — Foundry-side handlers.

## Implementation status

All planned fixes are implemented in the working tree and live-tested on
Foundry 14.363 (`shadowdark-test`):

- `evaluate.timeoutMs` is clamped to 5–180 seconds and forwarded only to the
  server RPC layer. A 16-second expression completed with
  `timeoutMs: 60000` and reported `evalMs: 16229.7`.
- `evaluate({background:true})` plus `job_result` completed a deliberate
  60-second job (`evalMs: 60635.5`) without a global polling stash.
- Results above 256 KiB return a bounded handle and preview. Live verification
  read a 300,059-byte result in chunks and deleted it explicitly. The store is
  capped by TTL, entry count, entry bytes, total bytes, and running jobs.
- `bridge_status` reports connected and last-seen metadata, probes
  `/api/status`, and supports restart-safe `FOUNDRY_URLS`.
- `reload_foundry` failures include the structured bridge diagnosis.
- `relaunch_client` is opt-in, loopback-only by default, and reads credentials
  only from environment configuration. After the GM left the world,
  `bridge_status` classified `foundry-up-no-users`; `relaunch_client` restored
  the GM bridge in 11,689ms.
- `create_scene` and `update_scene` translate v14 background, texture,
  foreground, level-fog, and exploration fields to the default embedded Level
  and `Scene.fog.mode`. Live create/update readback matched every probe field.
- `self_test` creates uniquely flagged Actor, JournalEntry/Page,
  RollTable/TableResult, and Scene/Level documents, then verifies guarded
  reverse cleanup. Live result: `pass: true`, four checks passed, four
  documents deleted, zero flagged residual documents.
- `screenshot` and `capture_scene` advance the PIXI ticker before rendering.
  Live hidden-tab probes moved queued Note placeables from `(0,0)` to their
  exact document coordinates.
- Automated coverage: `npm test` under `server/` covers status classification,
  timeout propagation, job/result bounds, v13/v14 Scene mapping, guarded
  self-test cleanup, relaunch configuration/join flow, and canvas flushing.

Implementation note: oversized results use a dedicated Foundry-side bounded
runtime store rather than the server `snapshot-store.js`, because evaluation
jobs execute and settle in the browser process. This keeps job state and
serialization in one lifecycle while preserving the same handle-based API.

## P1 — Long-running `evaluate` (the 15s wall)

**Symptom:** `Request to Foundry timed out after 15s` on bulk operations
(actor sweep, table migration). Worked around with a fire-and-poll hack
(`globalThis._report = null; promise.then(r => globalThis._report = r)` then
re-poll) — ugly and easy to get wrong.

**Where:** `server/lib/foundry-rpc.js` — `requestFoundry(tool, params,
targetUser, timeoutMs = REQUEST_TIMEOUT)` *already accepts a per-call
override*; the `evaluate` tool just doesn't expose it.

**Fix (two layers):**
1. **Expose `timeoutMs` through a raw `evaluate` tool handler** (`server/tools/
   runtime.js`): optional param, clamp to 5s–180s, and explicitly pass it as
   the fourth `callFoundry` argument. Zero bridge changes (the bridge has no
   response deadline of its own — the timeout is purely server-side).
2. **Job pattern for unbounded work:** `evaluate(expression, {background:
   true})` → bridge stores the running promise in a `Map<jobId, {promise,
   result?, error?, startedAt}>`, replies immediately with `{jobId}`. New tool
   `job_result(jobId, {waitMs})` → returns `{status: "running"}` or the
   settled result; entries GC'd after retrieval or 30 min. Bridge: ~40 lines;
   server: two thin tool defs.

**Acceptance:** a deliberately slow 60s evaluate completes via
`background:true` + `job_result` with no `globalThis` stash; plain `evaluate`
behavior unchanged; `timeoutMs: 60000` works for mid-length calls.

## P2 — Dead GM client is a dead end (worst failure mode)

**Symptom:** one `reload_foundry` never reconnected (Chrome discarded the
backgrounded tab). Server stayed healthy (`/api/status` → `users: 0`) but
every tool returned `No GM bridge connected` forever. Recovery required an
out-of-band browser automation to rejoin `/join` as Gamemaster.

**Fixes, in order of effort:**
1. **`bridge_status` tool** (`server/tools/server-local.js`, no Foundry
   round-trip): report connected and last-seen WS bridges + REST probes of
   bridge-advertised or configured (`FOUNDRY_URLS`) Foundry origins. Classify:
   `foundry-down` / `foundry-up-no-users` / `foundry-up-no-bridge` /
   `bridge-connected`.
2. **Harden `reload_foundry`:** on reconnect timeout, run the same diagnosis
   and return it in the error payload — "server up, users: 0 → the browser
   tab died; reopen <host>/join as Gamemaster (or run relaunch_client)"
   instead of a bare timeout. (`module/scripts/bridge.js` reload handler +
   the server-side wait loop.)
3. **`relaunch_client` (v2, opt-in):** server spawns a real Chrome via
   `puppeteer-core` (system Chrome path from config), navigates `/join`,
   selects the configured GM user, submits, and waits for the bridge WS to
   register. Config: `gmUser`, optional `gmPassword`, `chromePath` —
   localhost-only by default, disabled unless configured. This converts the
   one unrecoverable failure into a tool call. Prior art: headless-GM bots.

**Acceptance:** kill the Foundry tab manually → `bridge_status` names the
condition precisely; with (3) configured, `relaunch_client` restores a working
bridge with no human action.

## P3 — Dedicated tools lag Foundry schema changes (v14)

**Symptom:** `create_scene`'s `background` param silently no-ops on v14 —
Scene backgrounds moved to embedded **Level** documents (`scene.levels`,
default id `defaultLevel0000`). Burned a debugging session; `evaluate` was
the workaround. (Same class of issue as the v14 ownership-string and
`pack.configure` label changes.)

**Fixes:**
1. **Version-gated background handling** in the bridge's create/update-scene
   handlers: when `game.release.generation >= 14`, write `background.*` to
   the default Level doc (`scene.levels.get("defaultLevel0000").update(...)`)
   after creation; < 14 keeps the legacy top-level field.
2. **Schema-drift audit pass** over every tool that writes documents
   (world-authoring, canvas, snapshot): check fields against v14 (scene
   fog/foreground → levels; compendium ownership = role→level-NAME strings;
   `pack.configure` has no `label`; `TableResult.description` vs legacy
   `.text`). Output: a v13/v14 compatibility column in `TOOLS.md`.
3. **`self_test` tool:** creates uniquely-named throwaway docs (scene, actor,
   journal, table), round-trips every field the tools claim to set, reports a
   per-field pass/fail table, then deletes ONLY what it created. Run it after
   every Foundry core update — schema drift surfaces in one tool call instead
   of mid-task.

**Acceptance:** `create_scene` with a background renders on v14 with no
follow-up evaluate; `self_test` passes clean on 14.363.

## P4 — Canvas captures vs backgrounded tabs

**Symptom:** placeables created while `document.hidden === true` render at
(0,0) — PIXI render flags queue but never apply; `capture_scene` then shows a
stale/garbled canvas until a manual
`canvas.app.ticker.update(performance.now())`.

**Fix:** use a shared `flushCanvasRender` helper in the bridge handlers for
`capture_scene`, `screenshot`, and future PIXI canvas-reading tools,
immediately before capture; note the behavior in `TOOLS.md`.

**Acceptance:** create 20 notes via evaluate in a hidden tab → `capture_scene`
shows them in position with no manual kick.

## P5 — Quality of life (cheap, batch with P1)

- Oversized `evaluate` results: route through the existing
  `snapshot-store.js` and return a handle + preview instead of risking
  truncation.
- Error envelopes: include the `bridge_status` classification in every
  `No GM bridge connected` error (free once P2.1 exists).
